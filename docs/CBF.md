# Compact block filter nodes

Kyoto is a background Bitcoin peer-to-peer node. Build it once, retain both `CbfComponents.client` and `CbfComponents.node`, call `node.run()`, drain `client.next_info()` and `client.next_warning()`, and call `client.update()` or `client.updates()` continually. Each successful update is a caught-up filter boundary including downloaded matching blocks. Apply and persist it to the wallet before requesting the next update. The node remains connected while waiting for the next block.

`CbfBuilder.build(wallet)` preserves the single-wallet API and its `ScanType` recovery options. `build_with_wallets(wallets)` accepts a nonempty, fixed set of wallets with distinct external descriptors on one network, using `ScanType::Sync`. `client.updates()` returns a map from each wallet's `wallet.descriptor_id(KeychainKind::External)` string to its `Update`; it also works for a single-wallet node. `client.update()` is only valid for the single-wallet builder. Both update methods preserve subscriber work if their futures are cancelled. Separate simultaneous calls serialize on one receiver and consume successive boundaries, so use one application update loop.

For a wallet being recovered, create it with a suitable script lookahead (for example `lookahead = 1000` per keychain), then call `wallet.insert_checkpoint(birthday_block)` before building the multi-wallet node. The supplied height and hash must be trusted and lie before the wallet's first possible transaction: scanning starts strictly after that checkpoint. Persist this change. Kyoto starts at the minimum wallet checkpoint with a rewind of up to seven actual block heights where checkpoints are available; a sparse genesis-plus-birthday chain therefore starts at the birthday. This is a finite script window, not progressive gap discovery. Creating/loading with a larger lookahead is also required when resuming a wallet whose address usage may extend farther than its current window.

`Info::NewChainHeight`, `Info::CfHeadersProgress` and `Info::FiltersProgress` describe downloaded data. `Info::Synced { tip }` is emitted when an update method returns after processing a filter boundary; it does not mean the application has applied or persisted that update. A chain height above the last synced tip indicates scanning. Native download events and local synced events use independent queues, so an older `NewChainHeight` can still be received after a synced event. Compare heights. `client.chain_tip()` reports header-chain progress, which may be ahead of wallet scanning.

`client.rescan_from(height)` requests filters strictly after the specified height, within the node's locally available chain; `client.rescan()` restarts from the configured checkpoint. These commands do not change the node's wallet or script snapshot and can be ignored by the underlying node while it is still syncing headers. To add/remove wallets, change recovery lookahead, or reveal scripts beyond the snapshot, shut down the node, await termination, persist wallet state and rebuild with the new set. Ordinary receiving within the preloaded lookahead remains covered.

`client.broadcast(transaction)` sends a singleton package through the running node. `client.submit_package(transactions)` accepts a singleton or a parent followed by its spending child and sends data to a random connected peer. Success acknowledges transmission to at least one peer, not mempool acceptance or confirmation. `min_broadcast_feerate()` returns the maximum peer fee filter. `get_header(height)` looks up the local header chain. `peer_count()` counts all address types, while the compatible `peer_info()` method lists only IPv4/IPv6 peers. `connect(peer)` adds a peer.

When stopping, call `client.shutdown()` and then `node.await_termination(timeout_millis)`. Even if shutdown reports `NodeStopped`, await termination before releasing ownership. `is_running()` indicates request-channel availability and stop intent, not native thread teardown. A false termination result requires retaining ownership and waiting again: an already-running OS DNS resolver can delay runtime teardown. Dropping the last client or node requests cancellation. Calling `run()` more than once has no effect.

Peer persistence is intentionally left to the application and is not implemented by this wrapper. Reusing peers changes the privacy and bootstrap trade-off; do not equate maintaining the same node across blocks with persisting its address book across restarts.
