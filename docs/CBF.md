# Compact block filter nodes

Kyoto is a background Bitcoin peer-to-peer node. Build it once for the selected wallets and retain both `CbfComponents.client` and `CbfComponents.node`. For an owner whose Dart isolate or Flutter engine can disappear, configure `CbfBuilder.owner_lease_millis(ttl_millis)` before building, then call `node.run()`. The native runtime consumes wallet and diagnostic events internally. Use a Dart timer to call only the synchronous `renew_lease()`, `poll_updates()`, `drain_info()`, `drain_warnings()` and `status()` methods. These calls register no foreign future or callback. Choose a TTL of a few seconds with a renewal interval comfortably shorter than the TTL. The accepted TTL is 1..86400000 milliseconds; it begins at the first `run()` and uses a monotonic clock. Builds without this setting preserve the legacy lifetime and APIs.

`poll_updates()` immediately returns `None` or removes the oldest complete batch, a map from each wallet's `wallet.descriptor_id(KeychainKind::External)` to its `Update`. Apply and persist every returned update to its matching wallet. A single native consumer uses Kyoto's cancellation-safe subscriber; progress processing cannot steal or discard wallet work. Both single-wallet and multi-wallet builders support leased polling. The node remains connected between blocks while its owner renews the lease.

The prepared-batch FIFO holds at most **8 complete boundaries**, including every wallet in each boundary. It never coalesces or discards wallet updates. If enqueueing a boundary fills the queue, the native runtime stops immediately through its normal cancellation/termination path, before consuming another boundary. `status().last_error` explains that the owner must drain, apply and persist all batches, then rebuild. Already queued batches remain available after shutdown, lease expiry, overflow or native termination. Draining a stopped node cannot restart it. This fail-closed overflow policy bounds the wrapper queue without moving an unlimited backlog into Kyoto's upstream unbounded event channel. The bound is a batch count, not a byte or total-process memory limit: an individual update and a single in-progress scan can be large.

Each diagnostic FIFO holds at most **64 messages**. The info queue replaces an older `NewChainHeight`, `CfHeadersProgress` or `FiltersProgress` of the same kind with its latest occurrence, appending the replacement so surviving events retain their occurrence order. Other info and warning overflow discards the oldest diagnostic. `status().info_dropped` counts replacement and overflow in this wrapper, and `warnings_dropped` counts warning overflow. Both saturate at u64 maximum. They cannot count messages already dropped by bip157's own bounded logging channels. `drain_info()` and `drain_warnings()` remove their current contents immediately. Diagnostics are lossy; wallet batches are authoritative.

`status()` returns `running`, `terminated`, `synced_tip`, `last_error`, `info_dropped` and `warnings_dropped`. The synced tip is the latest queued wallet boundary, not application persistence or necessarily the current header tip. `Info::Synced { tip }` is emitted when a complete update is queued. Progress fractions describe downloads. A `NewChainHeight` above the latest synced height indicates scanning, while older height events can still appear. Apply and persist the batch before presenting it as durable wallet state.

On explicit shutdown, call synchronous `client.shutdown()` and poll synchronous `node.is_terminated()` or `client.status().terminated` from the timer until true. Even if shutdown reports `NodeStopped`, continue checking acknowledgement before releasing ownership or rebuilding. `is_running()` indicates request-channel availability and stop intent; true termination acknowledges that the OS thread and its Tokio runtime have exited and been joined. Expiry follows the same cancellation and acknowledgement path. `renew_lease()` rejects a stopped or already expired owner, even before the native timer has polled its deadline; it cannot revive a node. Dropping the last client or node also requests cancellation. Calling `run()` more than once has no effect.

Lease deadlines depend on native runtime scheduling and OS scheduling; they are not hard realtime guarantees. A long synchronous native operation can delay timer polling. An already-running blocking OS DNS resolver can delay complete runtime teardown after peer tasks have been cancelled, so `terminated` remains false until that work returns. Configured localhost peers bypass DNS in the offline lifecycle tests. No callback is made into Dart by polling-mode shutdown, expiry or disposal.

## Legacy asynchronous calls

Existing single-wallet `build(wallet)`/`update()` and multi-wallet `build_with_wallets(wallets)`/`updates()` remain available on builds without an owner lease. Legacy `next_info()`, `next_warning()`, `update()` and `updates()` can remain pending indefinitely. **They are unsafe if their owning isolate can die:** completing or cancelling their UniFFI futures can invoke a deleted Dart callback and abort the process, including during shutdown. Leased nodes reject these four methods immediately with `InvalidConfiguration` so they cannot compete with the internal consumer. Do not create these event futures on a polling-mode owner.

The other retained asynchronous requester methods (`chain_tip`, `get_header`, `broadcast`, `submit_package`, `min_broadcast_feerate`, `average_fee_rate`, `peer_info`, `peer_count`) and `node.await_termination` also use foreign futures. A future pending at owner death has the same callback risk. They remain compatible but are outside the callback-free owner-death contract; use the synchronous status and termination poll for lifecycle management, and coordinate a live owner before using asynchronous operations. Shutdown cannot make a previously registered legacy foreign callback safe after its isolate has disappeared. Never demonstrate legacy owner-death cleanup in the same process as a test runner; an abort is process-wide.

## Wallet and requester configuration

`CbfBuilder.build(wallet)` preserves the single-wallet API and its `ScanType` recovery options. `build_with_wallets(wallets)` accepts a nonempty, fixed set of wallets with distinct external descriptors on one network, using `ScanType::Sync`. On legacy clients `updates()` returns a descriptor-keyed map for either builder; `update()` is only valid for the single-wallet builder. Both preserve subscriber work if their futures are cancelled. Concurrent calls serialize on one receiver and consume successive boundaries, so use one application update loop.

For a wallet being recovered, create it with suitable script lookahead (for example `lookahead = 1000` per keychain), then call `wallet.insert_checkpoint(birthday_block)` before building the multi-wallet node. The supplied height and hash must be trusted and lie before the wallet's first possible transaction: scanning starts strictly after that checkpoint. Persist this change. Kyoto starts at the minimum wallet checkpoint with a rewind of up to seven actual block heights where checkpoints are available; a sparse genesis-plus-birthday chain therefore starts at the birthday. This is a finite script window, not progressive gap discovery. Loading with a larger lookahead is also required when resuming a wallet whose address usage may extend farther than its current window.

`rescan_from(height)` requests filters strictly after the specified height, within the node's locally available chain; `rescan()` restarts from its configured checkpoint. These commands do not change the wallet/script snapshot and can be ignored during initial header sync. To add/remove wallets, change recovery lookahead, or reveal scripts beyond the snapshot, shut down, acknowledge termination, persist wallet state and rebuild. Ordinary receiving within preloaded lookahead remains covered.

`broadcast(transaction)` sends a singleton package through the running node. `submit_package(transactions)` accepts a singleton or a parent followed by its spending child and sends data to a random peer. Success acknowledges transmission, not mempool acceptance or confirmation. `min_broadcast_feerate()` returns the maximum peer fee filter. `get_header(height)` looks up the local header chain. `peer_count()` counts all address types; compatible `peer_info()` lists only IPv4/IPv6. `connect(peer)` adds a peer. These controls do not replace the lifecycle restrictions above.

Peer persistence is left to the application. Reusing peers changes the privacy/bootstrap trade-off; keeping one node across blocks does not persist its address book across restarts.
